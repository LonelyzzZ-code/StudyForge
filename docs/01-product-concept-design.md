# StudyForge 产品概念设计

> 状态：定稿（v1.1，2026-10-19 增补学习问答 assistant 环节）
> 日期：2026-10-15
> 本文档为项目基准文档，后续所有设计与技术决策对照本文档执行。

## 一、产品是什么

**一句话：** 开源的、模型无关的 AI 学习内容引擎——用户输入「想学什么 + 现有基础 + 期望成果 + 可用时间」，系统生成成体系的学习路线、内容和测验，帮用户把新知识学到「掌握基础」的程度。

三个定位支柱：

1. **引擎，不是聊天机器人。** 内部是代码编排的确定性流水线（workflow），LLM 只在明确划定的三个位置被调用，行为可控、成本可预算。
2. **不带模型，self-host。** 用户接入任意 OpenAI 兼容 API（DeepSeek / GLM / OpenAI / Ollama 等），自带 key、自担成本、数据留在本地。
3. **生成质量是核心卖点。** 差异化不在「能对话」，在「路线 + 内容 + 测验成体系、带质检的一次性高质量生成」。

**不是什么：** 不是万能导师（不承诺精通）、不做学习社区、不替用户坚持——它负责把「学什么、学什么顺序、学到什么程度算会」这件事做扎实。

## 二、目标用户与领域边界

**用户：** 有明确目标和期限的学习者——备考（四六级 / 考研 / 证书）、掌握某项新技术技能。次级：隐私敏感想用自己模型的用户、基于引擎二次开发的开发者。

**领域切法：按学习模式，不按学科。** 只做「目标明确、进度可量化、练习可判分」的结构化学习。

- **首发三领域：** 编程技术、语言类、应试学科。入选标准：闭环可判分 + 能亲自判断生成质量（能调试 prompt）。
- **扩展单位：领域模板包**（内容结构模板 + 题型配比 + 判分规则 + 掌握度阈值）。新增领域 = 新增模板包，不改引擎，也是未来的社区贡献单位。
- **拒绝策略：** 范围外请求（如「学做饭」）明确告知不支持并列出支持领域，不硬生成低质量内容。

## 三、概念模型

系统只有五个核心概念：

| 概念 | 内容 |
|---|---|
| **学习请求 LearningRequest** | 用户的原始提示词：目标、基础、期望成果、可用时间 |
| **学习路线 Roadmap** | 知识点 DAG（有向无环图）。节点 = 知识点，携带细分知识点清单、依赖边、预计时长；支持线性 / 网状 / 递进各种拓扑 |
| **内容包 NodePackage** | 一个节点的全部产出物：讲义 + 摘要（供后续节点做上下文）+ 题库 + 实践任务 |
| **题目 Question** | 题干 + 选项/答案 + **标签组**（knowledge_points / skill / difficulty）+（简答题附）一句话标准答案与关键点清单 |
| **学习记录 Progress** | 节点完成状态、答题记录、错题标签统计 |

另有一个静态配置概念：**领域模板包 DomainProfile**，决定该领域的内容结构和题型配比。

## 四、产品运行流程

### 4.1 用户视角

```
输入学习请求
  → 收到学习路线（DAG 可视化，含依赖与时长）
  → 手动调整：删掉已会的 / 标记不感兴趣 / 重生成某分支
  → 按节点学习（打开即就绪内容）
  → 节点测验：概念记忆档 → 达标 80% → 解锁基础理解档 → 达标即节点通过
  → 答错 → 系统出同标签变式题；同一标签错 ≥2 次 → 提示重学该知识点
  → 实践任务：只给任务书（目标 + 要求 + 自查清单），自行实现，自行标记
  → 逐节点推进，完成整条路线
```

### 4.2 引擎视角（两条流水线）

**① 生成流水线（后台，按 DAG 拓扑顺序）**

```
路线生成（LLM）→ 代码校验（测环 / ID 存在性 / 覆盖度，失败带原因重试）
每节点依次：
  生成内容包（LLM，携带全局大纲 + 前序摘要 + 领域模板）
  → 质检（纯代码：知识点覆盖率、结构完整性、与前序的 embedding 重复度）
  → 通过 → 置「就绪」；不通过 → 带原因重生成 2~3 次 → 仍失败 → 置「存疑」放行
生成节奏跟随学习进度：始终保证当前节点 + 后续 3~5 个节点就绪，不全量生成
```

**② 学习流水线（前台，用户交互时）**

```
作答 → 选择/填空：代码规则判分（零延迟）
     → 简答：LLM 判分（核对关键点，理由须引用答案原文）
错题 → 记录标签 → 取标签生成变式题（LLM，同考点换情境，相似度落区间内）
标签统计 → 同标签错 ≥2 次 = 薄弱点 → 提示重学（重学已有内容，不碰路线）
```

## 五、AI 调用边界（引擎的关键设计）

全系统只有四处调用 LLM，其余全是本地确定性逻辑：

| 调用 | 职责 | 模型环节 | 频次 |
|---|---|---|---|
| 路线生成 | 学习请求 → DAG | planner | 每条路线 1 次 |
| 内容包生成 | 节点 → 讲义+摘要+题库+变式题 | generator | 每节点 1 次 |
| 简答判分 | 核对关键点命中 | grader | 每次简答作答 1 次 |
| 学习问答 | 学习中即时答疑（对话式、流式） | assistant | 用户主动触发 |

- 前三处为**引擎流水线调用**（系统发起）；第四处为**用户主动调用**（v1.1 增补）：学习者在节点页呼出问答窗，AI 携带当前节点上下文答疑。限制 LLM 面的初衷是压低系统侧的花费与不可控，用户主动提问属于其付费意愿最强的场景，不违背初衷。
- **四环节可分别配置模型**：planner 配强模型（质量敏感低频），generator 配性价比模型（高频），grader 配最便宜的小模型（任务极简），assistant 默认继承 generator 配置、可单独指定。
- 判分、质检、错题统计、调度全部不依赖用户 API——花钱和不可控的部分被压到最小面。
- **BYOK 兼容要求降到最低**：用户 API 只需支持文本生成；结构化输出不支持时走降级链（structured output → JSON mode → 提示词内嵌 schema + 解析重试）；上下文窗口自适应裁剪。

## 六、关键机制的设计理由（备忘）

1. **题目只考基础、简答只有一句话概念题**——产品面向「学新知识」的用户，精通靠实践任务和自己深入；题目简单化同时让出题、判分、掌握度判定三环节可控。
2. **错题处理 = 标签匹配，不做 AI 归因**——确定性、可解释、与模型能力解耦。单次错题不归因，同标签错 ≥2 次才定位薄弱点。
3. **实践任务只出题不评阅**——主观评阅砍掉，判分只剩简答一种。
4. **不做自动路线调整（一次性生成）**——用户手动调整属于生成阶段的修订；错题标签数据照常存储，未来若恢复「路线动态调整」（v2 方向），输入数据是现成的，零成本留后路。
5. **内容不引用外部链接**——规避通用领域的链接幻觉，内容自包含。
6. **内容预生成而非懒生成**——生成时携带全局大纲与前序摘要上下文，保证连贯、不重复、难度曲线合理；用学习速度天然掩盖生成耗时。

## 七、设计原则

1. **质量优先于覆盖面**——早期口碑取决于生成质量；质检是弱保证，用户反馈通道兜底（「这段没懂」触发定点重生成）。
2. **通用引擎 + 领域模板包**——引擎与领域解耦，领域可插拔。
3. **确定性优先**——能用代码做的绝不用 LLM；LLM 只做生成和最小化判分。
4. **模型能力解耦**——用户接入弱模型时，降级体验（判分多给原文引用、少做判断），不硬给不可靠结论。

## 八、边界：明确不做

体验型技能（烹饪 / 乐器 / 健身）、自动路线调整、账号系统、支付、社区、多语言界面、外部资源推荐。

## 九、已知风险与待验证参数

| 风险/参数 | 说明 | 验证阶段 |
|---|---|---|
| 质检是弱保证 | 用 LLM 审 LLM 不可靠，质检以代码层客观度量为主 | demo 阶段用真实生成结果调 |
| 变式题的变式度区间 | 太相似=重做原题，太远=考点漂移 | demo 阶段调参 |
| 选择题干扰项质量 | 要求「来自常见误解」+ 生成后校验区分度 | demo 阶段调 prompt |
| 答案泄露 | 题干不含答案线索；简答标准答案不与讲义原文一字不差 | demo 阶段校验 |
| 语言类内容事实准确性 | 无客观 validator（编程可运行验证），打磨成本最高 | 语言模板包阶段 |
| 前序摘要链失真 | 摘要的摘要会断层，需控制摘要长度与生成时机 | 架构阶段定规则 |
